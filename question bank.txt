--- TOPIC: Concepts & Theory ---

Q61. Explain the difference between a DATABASE and a DBMS. Give one example of each.

     ANSWER:
     A database is the organized collection of data itself (the actual stored information).
     A DBMS is the software system used to create, manage, and interact with that database.
     Example: The collection of patient records, appointment data, and doctor information
     stored on disk = the database. MySQL (the software you install and use to run
     queries on that data) = the DBMS.

Q62. What is functional dependence? Give a clear example using a real-world scenario.

     ANSWER:
     B is functionally dependent on A if knowing the value of A always and uniquely
     determines the value of B (written A -> B). Example: In a patient table,
     patient_id -> first_name, last_name, dob means that knowing the patient ID
     uniquely determines the name and date of birth. However, phone -> patient_name
     is NOT a functional dependency because two patients (e.g., parent and child)
     can share the same phone number, so phone does not uniquely determine a name.

Q63. Describe the three levels of database design (Conceptual, Logical, Physical).
     State TWO features that each level adds or specifies compared to the previous.

     ANSWER:
     Conceptual: The highest, most abstract level. Contains entity names and
     entity relationships only. Aimed at non-technical stakeholders.
     Logical: Adds attributes and primary/foreign keys to the conceptual model.
     Many-to-many relationships are resolved using bridge tables. Still not tied
     to any specific DBMS.
     Physical: The most detailed level. Adds table names, column names, and column
     data types. Tailored to the chosen DBMS (e.g., MySQL). Includes indexes,
     storage details, and performance considerations.

Q64. Explain why a many-to-many (M:N) relationship cannot be directly implemented
     in a relational database. What is the solution?

     ANSWER:
     A relational database requires each cell to hold a single value (no multi-valued
     cells). A direct M:N relationship would require one row to reference multiple rows
     in another table simultaneously, which violates this rule. The solution is to create
     a bridge (junction) table. This table contains the primary keys from both original
     tables as foreign keys, and each row represents one specific pairing. For example,
     a student-course M:N relationship is resolved by a "enrollment" bridge table
     with (student_id, course_id) as the composite primary key.

Q65. What is a secondary key? How does it differ from a primary key?
     Give a real-world example from the course materials.

     ANSWER:
     A secondary key is any key used for data retrieval that is NOT the primary key.
     It is not required to be unique. It narrows down search results but may still
     return multiple matches. A primary key MUST be unique and NOT NULL, and there
     is exactly one per table. Example: In Qatar, phone number is a common secondary
     key -- searching by phone narrows down the list to a few people, but since
     children and parents often share numbers, it is not unique and not a primary key.

Q66. Why is design described as "iterative" in this course? What are the practical
     consequences of taking shortcuts in early design stages?

     ANSWER:
     Iterative means you rarely get the correct design in a single pass. You make
     educated guesses, ask stakeholders questions, discover problems, and revise the
     model repeatedly. Taking shortcuts early -- like skipping proper normalization or
     ignoring business rules -- creates problems later during implementation:
     redundant data, update anomalies, difficulty enforcing constraints, and
     expensive redesign of tables that already contain live data.

Q67. Explain the difference between a centralized and a distributed database.
     Give one real-world advantage and one real-world disadvantage for each.

     ANSWER:
     Centralized: All data in one location. Advantage: simple to administer, one
     consistent copy of data. Disadvantage: single point of failure (e.g., airline
     systems going down and canceling thousands of flights).
     Distributed: Data in multiple locations. Advantage: faster local access, redundancy
     means one node failing doesn't cause total data loss. Disadvantage: much harder to
     configure and maintain, risk of data inconsistency across nodes.

Q68. What is a surrogate key? Why are surrogate keys the most common type of
     primary key used in practice?

     ANSWER:
     A surrogate key is an artificial, system-generated identifier with no business
     meaning -- typically an auto-incremented integer. They are the most common PK
     because: (1) they are always unique; (2) they never need to change (unlike
     business data like email or phone); (3) they are small integers, making
     joins fast; (4) they are simple to generate with AUTO_INCREMENT and require
     no thought from the developer inserting data.

--- TOPIC: SQL ---

Q69. Explain the difference between WHERE and HAVING. Why can't you use an
     aggregate function in a WHERE clause?

     ANSWER:
     WHERE filters individual rows BEFORE grouping occurs. HAVING filters groups
     AFTER the GROUP BY clause has been applied. Aggregate functions (COUNT, SUM,
     AVG, etc.) operate on groups of rows, not individual rows. Since WHERE runs
     before grouping, groups don't yet exist at that point, so aggregate functions
     have nothing to operate on. The correct clause for filtering by aggregate
     results is HAVING.

Q70. Describe what ON DELETE CASCADE does and explain why the course materials
     say it is "generally not a good idea."

     ANSWER:
     ON DELETE CASCADE means that when a parent row is deleted, all child rows
     that reference it via a foreign key are automatically deleted as well.
     The course materials say it is generally not recommended because in most
     real systems you want to preserve history. For example, if a patient is
     removed, you probably still want to keep the appointment records for
     auditing, billing, or medical history purposes. Auto-deleting them silently
     risks permanently losing important data.

Q71. What is an index in MySQL? Describe the tradeoff between having too few
     and too many indexes.

     ANSWER:
     An index is a separate data structure that maps column values to the row
     locations where they appear -- like the index at the back of a book. It
     speeds up SELECT queries that use that column in a WHERE clause.
     Too few indexes: queries perform full table scans (type: ALL in EXPLAIN),
     which is slow for large tables.
     Too many indexes: INSERT, UPDATE, and DELETE operations become slower because
     every write must also update all indexes. The database also uses more disk space.
     The correct approach is to index only columns that are frequently searched.

Q72. Explain the difference between DROP TABLE, DELETE, and TRUNCATE.
     When would you use each?

     ANSWER:
     DELETE: Removes specific rows matching a WHERE condition (or all rows if no WHERE).
     It can be rolled back before a COMMIT. It does NOT remove the table structure.
     TRUNCATE: Removes ALL rows from a table quickly. Cannot be rolled back in most
     DBMS. Keeps the table structure. Faster than DELETE for clearing a table.
     DROP TABLE: Completely removes the table AND its structure from the database.
     Cannot be undone. Use when you no longer need the table at all.

Q73. A VIEW does not store data. Explain what actually happens when you
     query a view, and list two situations where views are useful.

     ANSWER:
     When you query a view, MySQL re-executes the underlying SELECT statement
     that defines the view and returns the results as if it were a real table.
     No data is physically stored in the view itself.
     Useful situations: (1) Security -- you can grant users access to a view
     that shows only certain columns or rows, hiding sensitive data. (2) Simplification
     -- complex multi-table joins or calculations can be defined once as a view,
     then queried simply with SELECT * FROM view_name.

Q74. Explain what a full table scan is, how to detect one in MySQL,
     and what you can do to fix it.

     ANSWER:
     A full table scan means MySQL reads every row in the table to find matching
     results, rather than jumping directly to relevant rows. This is slow for
     large tables. Detection: run EXPLAIN before the query -- look for type: ALL
     and key: NULL, which means no index was used.
     Fix: create an index on the column being searched in the WHERE clause.
     Example: CREATE INDEX idx_phone ON patient(phone); -- then re-run EXPLAIN
     and you should see type: ref or const instead of ALL.

Q75. Explain the difference between SELECTION and PROJECTION in relational algebra,
     and explain why this creates confusion in SQL.

     ANSWER:
     Selection (σ) filters rows based on a condition -- it is a horizontal operation.
     Projection (π) filters columns -- it is a vertical operation.
     In SQL, the confusion arises because the keyword SELECT performs projection
     (choosing which columns to show), while the WHERE clause performs selection
     (filtering rows). Students read "SELECT" and think it means "selection" from
     relational algebra, but it actually means projection. The WHERE clause is the
     real "selection" operator.

--- TOPIC: Design & Mapping ---

Q76. Given this business scenario: "Each student can enroll in many courses, and
     each course can have many students enrolled." Describe step by step how you
     would implement this in a relational database.

     ANSWER:
     This is a M:N relationship. You cannot implement it directly.
     Step 1: Create the student table with student_id as PK.
     Step 2: Create the course table with course_id as PK.
     Step 3: Create a bridge table (e.g., enrollment) with:
       - student_id (FK referencing student)
       - course_id (FK referencing course)
       - The composite (student_id, course_id) becomes the PK.
     Step 4: You may add additional attributes to the bridge table
     (e.g., grade, semester) if the relationship itself has properties.

Q77. In a 1:1 relationship where both sides are optional (an instructor may or
     may not have an office, and an office may or may not have an instructor),
     where should the foreign key go? Explain your reasoning.

     ANSWER:
     When both sides are optional, the database designer can choose either side
     for the foreign key placement. The practical consideration is: which entity
     is more likely to have the association? If most instructors eventually get
     an office, put the FK in the instructor table. If offices are often unassigned
     for long periods, put the FK in the office table. There is no single universally
     correct answer -- it is a design judgment call.

Q78. What features does the Logical model add compared to the Conceptual model?
     Why do we still NOT specify data types at the logical level?

     ANSWER:
     The logical model adds: attributes for each entity, primary keys, and foreign
     keys. It also resolves M:N relationships using bridge tables.
     Data types are not specified at the logical level because the logical model
     is intentionally independent of any specific DBMS. Different systems handle
     types differently (e.g., MySQL's VARCHAR vs. Oracle's VARCHAR2). Specifying
     types would tie the design to one platform, defeating the purpose of the
     logical model as a portable, DBMS-agnostic representation.

--- TOPIC: MongoDB ---

Q79. Explain the difference between EMBEDDING and REFERENCING in MongoDB.
     List one advantage and one disadvantage of each.

     ANSWER:
     Embedding: Storing related data inside the same document.
       Advantage: All data retrieved in a single query; supports atomic operations.
       Disadvantage: Document can grow large (16MB limit); overhead if you often
       only need part of the document.
     Referencing: Storing an _id reference to a document in another collection
     (like a foreign key in SQL).
       Advantage: Smaller documents; data doesn't get duplicated; frequently accessed
       data can be queried independently.
       Disadvantage: May require multiple queries to retrieve all related data.

Q80. What is the 16MB document limit in MongoDB, and why does it exist?
     How does it influence document design decisions?

     ANSWER:
     MongoDB limits each document to 16MB. This exists to ensure no single document
     consumes too much RAM during processing or too much bandwidth during replication
     between cluster nodes. It influences design by discouraging unbounded array growth
     -- if visits or comments can number in the thousands, embedding them all would
     eventually hit the limit. In those cases, referencing (storing child documents
     in a separate collection) is preferred.

Q81. Describe the One-to-Few, One-to-Many, and One-to-Squillions patterns in MongoDB.
     When should you use each?

     ANSWER:
     One-to-Few (embed directly): Use when the "many" side has only 2-20 items
     and you rarely need to query those items independently. Example: multiple
     addresses for one patient.
     One-to-Many (array of references in parent): Use when there are up to a few
     thousand child records and the child documents may need to stand alone.
     Example: a patient with many visits stored in a separate visits collection,
     with an array of visit _ids in the patient document.
     One-to-Squillions (parent reference in child): Use when child records are
     extremely numerous. Store a reference to the parent in each child document
     (like a SQL foreign key). Example: log entries for a server -- potentially
     millions of logs per server.

Q82. What is $elemMatch in MongoDB and when is it necessary?

     ANSWER:
     $elemMatch is a query operator used to search arrays of embedded objects.
     It specifies that ALL conditions inside the $elemMatch must match within
     the SAME array element. It is necessary when you have an array of objects
     and you need to find documents where a single element satisfies multiple
     conditions simultaneously. Without $elemMatch, MongoDB would check each
     condition against any element in the array independently, potentially
     producing incorrect matches.

Q83. Explain what $unwind does in a MongoDB aggregation pipeline.
     Why is it useful and what does the output look like?

     ANSWER:
     $unwind deconstructs an array field from the input documents and outputs
     one document per array element. For example, if a patient document has a
     visits array with 3 visits, $unwind produces 3 separate documents, each
     with one of the original visits and all the other patient fields intact.
     This makes array data look and behave like a table, making it much easier
     to filter, group, and aggregate individual array elements. It is useful
     when you need to count visits per doctor, filter specific visit dates, or
     compute statistics at the visit level rather than the patient level.

Q84. Compare the MongoDB aggregation pipeline to SQL GROUP BY.
     Map $match, $group, $project, and $sort to their SQL equivalents.

     ANSWER:
     $match (before $group)  --> SQL WHERE   (filter rows before grouping)
     $group                  --> SQL GROUP BY + aggregate functions (SUM, AVG, etc.)
     $match (after $group)   --> SQL HAVING  (filter groups after aggregation)
     $project                --> SQL SELECT column list (choose which fields to show)
     $sort                   --> SQL ORDER BY (sort results)
     Key difference: in SQL, these are fixed clauses in a fixed order.
     In MongoDB, pipeline stages can be reordered and repeated as needed.

Q85. Why does the course say that JOINs sound "like the opposite of normalization"?
     Explain the relationship between normalization and JOINs.

     ANSWER:
     Normalization is the process of splitting data across multiple tables to
     eliminate redundancy and anomalies. JOINs are the mechanism for recombining
     that split data at query time to produce a unified result. They appear to be
     opposites because normalization separates data while joins reunite it.
     However, they work together: we normalize to store data cleanly, then use
     JOINs to reassemble the data we need for specific queries without duplicating
     storage.

Q86. What is the difference between a relational database (MySQL) and a
     key-value / document store (MongoDB)? Give one scenario where each
     is a better choice.

     ANSWER:
     Relational (MySQL): Fixed schema, all records have the same structure,
     relationships enforced via FK constraints, queries via SQL.
     Document (MongoDB): Flexible schema, each document can have different fields,
     no enforced relationships, queries via MQL.
     MySQL better: Banking system -- data is highly structured, relationships are
     critical, and consistency matters.
     MongoDB better: A product catalog for an e-commerce site where different product
     categories have completely different attributes -- rigid schemas would waste space
     or require many nullable columns.

Q87. List the five general rules for MongoDB document design from the course.
     For each rule, give a one-sentence summary.

     ANSWER:
     Rule 1: Favor embedding unless there is a compelling reason not to.
     Rule 2: Needing to access an object on its own is a compelling reason not to embed it.
     Rule 3: Avoid joins/lookups if possible, but don't be afraid if they give a better schema.
     Rule 4: Arrays should not grow without bound (more than a couple hundred = use references).
     Rule 5: Structure data to match your application's actual query and update patterns.

Q88. What are the constraints available in MySQL DDL? Briefly describe each one.

     ANSWER:
     NOT NULL: Column must always have a value; cannot be empty.
     UNIQUE: All values in the column must be different; allows one NULL.
     DEFAULT: Provides a fallback value when no value is supplied during INSERT.
     CHECK: Validates that values satisfy a specified condition (e.g., age >= 18).
     PRIMARY KEY: Uniquely identifies each row; combines UNIQUE and NOT NULL; one per table.
     FOREIGN KEY: References the primary key of another table; enforces referential integrity.

Q89. In MySQL Workbench physical modeling, what do the following symbols represent?
     Yellow key, Red key, Blue filled diamond, Red open diamond.

     ANSWER:
     Yellow key: The column is a primary key.
     Red key: The column is both a foreign key AND part of the primary key
              (common in bridge tables).
     Blue filled diamond: The column is mandatory (NOT NULL).
     Red open diamond: The column is an optional foreign key (nullable FK).

Q90. Explain why the course materials warn: "Specifying an incorrect condition
     in UPDATE or DELETE could result in updating or deleting everything."
     What best practice does this lead to?

     ANSWER:
     UPDATE and DELETE statements without a WHERE clause apply to EVERY row in the
     table. Even a WHERE clause with a subtle error (wrong column, wrong value)
     could match far more rows than intended. Best practices: (1) Always double-check
     your WHERE condition with a SELECT first to confirm which rows it matches before
     running UPDATE/DELETE. (2) Work in a transaction so you can ROLLBACK if
     something goes wrong before committing. (3) Make backups before running
     bulk data operations.

Q149. [Written] Explain when you would use EMBEDDING versus REFERENCING in MongoDB.
      Give a specific example of each from a medical clinic scenario.

      ANSWER:
      Embedding: Use when related data is small, always accessed with the parent,
      and doesn't need to be queried independently. Example: embed a patient's
      last_vitals (height, weight, heart_rate) directly inside the patient document
      because vitals are always viewed as part of the patient record, they are few
      in number, and we never query vitals without wanting the patient info too.

      Referencing: Use when data can grow large, needs independent access, or is
      shared across multiple documents. Example: store visits in a separate 'visits'
      collection and include a patient_id field in each visit document (like a FK).
      This is because a patient can have hundreds of visits over years, and medical
      staff may want to query all visits across all patients without loading every
      patient's full document.

      ANSWER:

      db.cars.createIndex({ manufacturer: 1 })

      -- Step 2: Run query with explain to verify index use
      db.cars.find({ manufacturer: "Toyota" }).explain("executionStats")

      -- In the output, look for:
      --   "stage": "IXSCAN"  --> index is being used (GOOD)
      --   "stage": "COLLSCAN" --> no index used (BAD)
